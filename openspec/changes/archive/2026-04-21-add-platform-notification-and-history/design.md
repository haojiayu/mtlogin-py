## Context

当前实现把任务配置存放在 `web:task_settings` 这一个 JSON blob 中，由 [app.py](/Users/haojiayu/Documents/me/github/mtlogin-py/app.py) 读取后直接拼成 `mtlogin.Config`，调度器也只会执行这一份配置。页面上只有一个“任务配置”表单，因此平台参数、通知参数、登录凭据和调度参数没有独立生命周期，更无法为多个账户保存历史执行记录。

这次变更需要把配置中心从“单条任务设置”升级为“平台 + 通知渠道 + 登录账户 + 执行记录”四类实体，同时保持管理员登录机制和现有 `mtlogin.JobServer` 的核心执行逻辑可复用。项目仍使用 Flask + SQLite，本次设计不引入额外服务或队列。

## Goals / Non-Goals

**Goals:**
- 在同一个 SQLite 数据库中引入平台、通知渠道、账户、账户通知关联、执行记录的数据模型。
- 保留内置 `mt` 平台，并将其 `API Host`、`API Referer` 固定为只读配置。
- 支持维护多个 `tg` 通知渠道，并允许账户勾选多个通知渠道。
- 将调度模型切换为“按账户执行”，并把每次执行结果持久化为可查询记录。
- 为旧版单条任务配置提供一次性迁移，避免升级后配置丢失。

**Non-Goals:**
- 本次不实现新的平台执行器；运行逻辑仍以 `mtlogin` 为核心，仅内置 `mt` 平台可执行。
- 本次不改造管理员认证、会话机制或日志文件格式。
- 本次不引入异步任务队列、外部数据库或前后端分离架构。

## Decisions

### 1. 在现有 SQLite 中增加结构化表，而不是继续扩展 KV JSON

新增 `platforms`、`notification_channels`、`accounts`、`account_notifications`、`execution_records` 表，现有 `kv` 表继续保留给管理员账号和运行时摘要状态使用。`SettingsStore` 负责初始化 schema、执行迁移和提供 CRUD 查询接口。

原因：
- 平台、通知渠道和账户都需要列表管理与关联关系，继续存成单个 JSON 会使筛选、约束校验和迁移都变得脆弱。
- 执行记录需要按账户、平台、状态、时间查询，必须具备结构化索引字段。

备选方案：
- 把所有列表继续保存在 `kv` 的多个 JSON key 中。放弃，因为执行记录查询和多实体关联会明显复杂化。

### 2. 内置 `mt` 平台作为受保护记录，账户通过外键关联平台

首次启动迁移时自动写入一条内置平台记录 `code=mt`，该记录默认启用，`api_host=api.m-team.io`、`referer=https://kp.m-team.cc/`，在 UI 中只读展示，不允许删除。账户表保存 `platform_id`，运行时由平台配置补全 `api_host` 和 `referer`。

原因：
- 用户要求当前只支持 `mt`，且该平台的 API 参数固定。
- 平台单独建模后，账户表不再复制平台级 API 字段，避免同一平台多账户配置不一致。

备选方案：
- 继续把 `api_host`、`referer` 放在账户表中。放弃，因为这会破坏“平台配置列表”的职责边界。

### 3. 通知发送从 `JobServer` 中解耦，改为按账户关联渠道发送

执行流程保留 `JobServer.run_once()` 负责登录与状态刷新，但新增 `NotificationDispatcher` 负责根据账户勾选的通知渠道逐条发送结果通知。为了避免重复通知，需要给 `JobServer` 增加“禁用内置通知”的执行路径，或将通知逻辑拆分为可选步骤。

原因：
- 当前 `mtlogin.Config` 只能表达一组 Telegram 配置，无法直接表示“一个账户绑定多个 TG 渠道”。
- 将通知调度提升到 Web 层后，可以按账户读取关联渠道并逐个发送，扩展到其他通知类型时也更自然。

备选方案：
- 把多个 TG 渠道合并成一份配置，在 `Config` 中硬塞列表字段。放弃，因为会把脚本层的数据结构和 Web 管理结构耦合得更重。

### 4. 调度器改为按账户计算下一次执行时间，并把每次执行写入历史表

`BackgroundScheduler` 不再只读取一份 `task_settings`。它需要加载所有启用账户，过滤掉无效 `crontab`，计算最早到期的账户并串行执行。每次执行后都写入 `execution_records`，运行时摘要状态则保存最近一次执行结果和下一次计划，供仪表盘顶部展示。

原因：
- 账户已经列表化后，调度单位必须从“全局配置”变为“账户”。
- 历史查询不能再依赖日志文件或单条 `runtime_state` 快照。

备选方案：
- 为每个账户启动一个独立线程。放弃，因为线程数会随着账户增长而失控，且停止/重载管理更复杂。

### 5. 升级时迁移现有单配置到默认账户和通知渠道

如果旧 `web:task_settings` 中存在 M-Team 凭据、调度配置或 Telegram 参数，初始化时自动创建：
- 内置 `mt` 平台；
- 一条默认账户（例如名称可用旧用户名或 `migrated-account`）；
- 一条默认 `tg` 渠道（仅当旧 Telegram 参数存在时）；
- 账户与通知渠道关联；
- 保留原 `web:task_settings`，但新页面仅读取新表结构。

原因：
- 现有用户升级后不应手工重录全部配置。
- 保留旧 key 便于回滚和排查迁移问题。

备选方案：
- 不迁移，要求管理员手工重建数据。放弃，因为会直接造成可用性回退。

## Risks / Trade-offs

- [迁移逻辑把旧字段映射错位] → 在迁移后写入明确的默认名称，并保留原始 `web:task_settings` 作为回退依据。
- [多账户调度后，顶部“当前状态”不再能完整代表所有账户] → 顶部摘要只展示最近一次执行结果，同时在账户列表和执行记录页呈现细粒度状态。
- [通知逻辑从 `JobServer` 中抽离后，脚本模式和 Web 模式行为可能分叉] → 保持脚本模式沿用原有单渠道通知，只有 Web 多账户路径走 `NotificationDispatcher`。
- [执行记录不断增长导致 SQLite 表变大] → 首期先提供查询与分页，后续如有需要再补充清理策略。

## Migration Plan

1. 在应用启动时执行 schema 初始化，确保新表和必要索引存在，并插入内置 `mt` 平台。
2. 检查旧 `web:task_settings`；若新表为空且旧配置存在，则迁移出默认账户和默认 `tg` 渠道。
3. 将后台页面拆分为平台管理、通知管理、账户管理、执行记录查询四个区域，并保持管理员登录与日志查看功能不变。
4. 切换调度器为账户级执行，保存执行记录和最新运行摘要。
5. 验证手动执行、定时执行、通知发送和历史查询后，再更新 README。

回滚策略：
- 保留 `kv` 表中的旧配置键值；
- 如需快速回滚，可恢复旧页面读取逻辑并忽略新表，不需要还原数据库文件。

## Open Questions

- “立即执行一次”在 UI 上是做成账户行内按钮，还是保留一个“执行全部启用账户”的入口；本设计默认优先实现账户行内执行。
- 执行记录是否需要清理策略或导出能力；本次先不实现，只保留查询。
- 非 `mt` 平台的录入界面是否在本次直接放出；本设计仅保留数据模型扩展位，首期 UI 只展示内置 `mt` 平台。
